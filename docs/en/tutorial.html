1. Library layout

AstroTool builds on four areas at the root of your library: sessions, stacks, processed, calibration_library. A session now stores its raw frames split into captures, because a single night often involves more than one camera/filter combination (e.g. a short OSC test and a long mono sequence on the same target):

<ROOT>/
├── sessions/<TARGET>/<YYYY-MM-DD>/
│   ├── captures/<slug>/
│   │   └── lights/   flats/   darks/   biases/
│   ├── captures/<other-slug>/...      # a night can have more than one capture
│   └── README.txt                        # notes you fill in by hand: Bortle, SQM, seeing...
├── stacks/<TARGET>/<YYYY-MM-DD>/<slug>/
├── processed/<TARGET>/<YYYY-MM-DD>/<slug>/
└── calibration_library/
    ├── darks/<exp>sec_<temp>deg/       # e.g. 300sec_-10deg
    ├── flats/
    └── biases/
  • sessions: the raw, original frames, grouped by capture (captures/<slug>). A capture records the sensor mode (OSC/mono), its character (broadband/narrowband/dual-band), and the exact filter. Nothing here is ever overwritten or deleted, this is the single source of truth.
  • stacks: the stacked intermediate results, mirroring the same <slug>. You can always regenerate these from sessions if you lose them.
  • processed: the final, post-processed images. This is the publish-ready state.
  • calibration_library: reusable master dark/flat/bias frames, filed by exposure and temperature.
Older library? If your session folders contain lights/, flats/, darks/, biases/ subfolders directly (no captures/ level), you don't need to change anything: AstroTool's scanner recognizes this older shape too and handles it correctly, including odd folder names like lights_osc. The app's Library section has a Conversion wizard that can, on request, transparently reorganize old sessions into the new captures/<slug> form (with a preview, reversibly), but this is entirely optional. The CLI's new-session command also still creates this classic, capture-less four-folder layout.

2. Naming rules

The target name and the date folder's name aren't free text: the tool reads them to figure out which frame belongs to which target and which night. Data inside a capture (sensor mode, filter) now lives in its own fields, but the date-level naming rules below are unchanged:

PatternMeaningExample
<catalog>_<name>target folder name, spaces replaced with _, everything else filtered outIC1805-1848_Heart_and_Soul_Nebula
YYYY-MM-DDsession date, strictly ISO format2026-03-15
-N suffixa second (or Nth) run on the same target and night2026-04-06-2
two dates joinedseveral nights combined into one session2026-02-25_2026-03-15
-OSC labela deliberately flagged deviation (e.g. an OSC-camera frame next to a mono sequence)2026-03-15-OSC
_hibas labela bad night: the tool deliberately excludes it from statistics2026-03-15_hibas

These patterns can be overridden in config.json (intentional.runSuffix/dateRange/labels), but the defaults recognize exactly these four cases. Date-level suffixes like -OSC survive because they operate at the session/date level; per-capture OSC/mono and filter data complements this, it doesn't replace it.

3. A night's workflow

  1. Import wizardplug in the card or volume (e.g. ASI Air, a camera card), the wizard classifies the found files by FITS IMAGETYP/DATE-OBS or Exif date, you pick or create the target session and capture, and after an itemized preview it copies the files with a SHA-256-verified, receipted copy. It never touches the originals on the card.
  2. Library checkthe Library section's Health view shows calibration gaps, duplicates, and audit findings before you stack anything.
  3. Review frames ("blink")opened from the Projects page: frame-level accept/reject, step with the arrow keys, A accepts, X rejects, U clears the decision and moves on.
  4. Link calibrationthe app hardlinks the matching master dark/flat/bias frames next to the session or capture, with a preview; also reachable from a night's context menu.
  5. Stack in Siril or DSSAstroTool doesn't stack for you: it exports the best frames (hardlink + .dssfilelist + Siril script), which you load into your own tool as usual.
  6. Plan and trackthe Planning page helps schedule the next clear night, and the Nights page shows your observations so far and their quality.
Which one, when? Before a clear evening, Planning (what's worth shooting tonight); on a cloudy or stay-in evening, Projects (where each target's processing stands: what still needs data, what just needs stacking or post-processing). The same steps are also available from the command line if you prefer: astrotool scan → astrotool audit → astrotool rate → astrotool stacklist → your own stacking tool → astrotool report; see the CLI reference.

4. Calibration crash course

Dark: measures thermal noise at the same exposure, temperature, and gain; needs regular refreshing because the sensor's temperature drifts. Flat: measures optical vignetting and dust; needs retaking any time the camera or focus moved (rotator position matters too). Bias: the sensor's readout pedestal; rarely changes, but the gain and offset combo has to match exactly.

Under calibration_library/darks/ the folder-naming convention is <exp>sec_<temp>deg (e.g. 300sec_-10deg): this is how the tool figures out which dark matches which capture parameters.

astrotool calib expects an exact match on camera, gain, offset, and temperature: it never guesses a false match, and it also watches the flat's rotator position, because a rotated flat isn't valid for the session. Calibration linking (from the Calibration view, a night's menu, or from the CLI's link-calib) hardlinks the matching master frames next to the session or capture, always with a preview: it will never overwrite a file.

5. Safety

What the tool writes

  • Its own working directory: .astro_tool/ (index, exports, reports, suggestion scripts)
  • New session and capture folders plus a README template (from the import wizard, or the CLI's new-session/capture create commands)
  • A SHA-256-verified, receipted copy on import; the source (card, volume) stays untouched
  • Hardlinks for calibration linking and stacking export, never in place of the original files
  • An internal SQLite index of the metadata

What it never does

  • Never deletes anything in your image library; whatever disappears from its spot goes to the archive (quarantine) instead
  • Never overwrites the original light/flat/dark/bias files
  • Never runs any suggestion script automatically
  • Only reads README.txt, never writes to it

Iron rule

The tool never permanently deletes anything in your image library. In the app, this is handled by the Archive map: you can review audit and cleanup findings and move them to quarantine, and whatever disappears from its spot can be brought back. From the command line, the same logic applies: audit/cleanup --suggest only flags things (a list of findings) and writes a reviewable .sh suggestion script into .astro_tool/suggestions/, which you review and run at your own discretion. The tool itself never performs a file operation outside your library except in its own .astro_tool/ workspace.
